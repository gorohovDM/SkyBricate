## Схема 2 и внутренний DataStore

Скрытое world setting по-прежнему только `skybricate.data`, default `{"schemaVersion":2,"systems":{}}`. Общего корневого `properties` больше нет. Каждый `systems[craftingSystemId]` содержит:

```json
{
  "properties": {"propertyId": {"name": "Название", "description": ""}},
  "categories": {},
  "components": {},
  "rules": {
    "limitByCheck": false, "successLimit": 0, "outcomeLimits": {},
    "prioritySpecial": false, "propertyOrder": []
  }
}
```

`createProperty(systemId, input)`, `updateProperty(systemId, propertyId, patch)`, `deleteProperty(systemId, propertyId)` теперь требуют ID системы. Создание при необходимости создаёт system entry; чтение/открытие вкладки ничего не создаёт. ID свойства стабилен при переименовании, по умолчанию randomUUID; уникальность требуется внутри системы. Совпадающие IDs в разных системах допустимы и не связывают каталоги. Удаление чистит категории, компоненты и propertyOrder только этой системы. Assign/rules допускают ссылки только на её собственный каталог. Остальные методы этапа 3 сохраняются.

Валидация по-прежнему строгая: неизвестные поля/версии, повреждения, опасные ключи, висячие/повторные ссылки, неверные лимиты отклоняются. Очередь одного экземпляра перечитывает setting перед каждой записью, повторно проверяет GM, копирует аргументы и переживает отказ сохранения. Успех после fulfilled settings.set. Между клиентами GM остаётся last write wins; отдельной блокировки нет.

Пользователь подтвердил, что схема 1 содержит только тестовые данные: миграции нет. Строго валидная схема 1 распознаётся `hasLegacyData()` только для предложения сброса. Вкладка сообщает об устаревшем общем справочнике и отсутствии миграции. Сначала «Сбросить старые тестовые данные», затем отдельная кнопка «Удалить старые тестовые данные и начать с пустых» с явным предупреждением об удалении всех старых свойств, назначений и правил SkyBricate в мире. `resetLegacyData()` стоит в той же очереди и снова проверяет GM и полную старую схему при исполнении. Записывает только пустую схему 2 в `skybricate.data`; Fabricate settings/stores/documents не изменяет. Повреждённые, неизвестные и будущие схемы не получают кнопку сброса и не перезаписываются. Если данные сменились между подтверждением и исполнением, сброс отклоняется. Это не механизм восстановления произвольных повреждённых данных.

## Проверенный контракт Fabricate 1.9.10

Адресно прочитаны `TagsCategoriesView.svelte`, `VocabularyPanel.svelte`, `InlineVocabularyAdd.svelte`, `Chip.svelte`, стили и участок `CraftingSystemManagerRoot.svelte`, подключающий представление. Upstream SHA `5bf36ddf950619317e41737acd3bfa1305591a26`. Исходники Fabricate не изменены. Нового коннектора нет.

`TagsCategoriesView` имеет локальный список трёх вкладок recipe/component/tag. `activeTab` передан root, обработчик root только присваивает `tagsActiveTab`; публичной регистрации вкладки нет. Поэтому адаптер привязан к версии и DOM: единственный `.manager-tags-categories`, единственный `.manager-vocabulary-tabs[role=tablist]`, три ожидаемые native buttons с ID/aria-controls/data-vocabulary-tab и единственный native `.manager-tags-categories-workspace[role=tabpanel]` с согласованными ID/aria-labelledby. Неизвестная/неоднозначная структура блокирует монтаж/запись с одним предупреждением GM на app. Отсутствие host означает другую страницу и не вызывает предупреждение.

Четвёртая кнопка добавляется в штатную полосу, workspace — рядом с native workspace. При активации адаптер временно скрывает native workspace и владеет только aria-selected/tabindex/active class native tabs. При выборе штатной вкладки сначала восстанавливает эти значения, затем пропускает click к исходному Svelte обработчику. При внешней смене native selection возвращает состояние текущего native workspace. Собственные tab/panel IDs уникальны между app sessions. ArrowLeft/ArrowRight/Home/End охватывают четыре вкладки и переводят фокус; Enter/Space используют обычное поведение button.

Слушатели click/keydown ограничены tablist. Сайдбар и внешние маршруты, подтверждения dirty drafts, методы Fabricate, stores и drafts не перехватываются и не записываются. При снятии вкладки восстанавливаются принадлежащие адаптеру изменения DOM, снимаются слушатели/подписки/observers. Подписки selectedSystemId/viewState и observer корня сохранены из первого варианта: ID/projection gap синхронно снимает старый редактор; повторные render не дублируют вкладку; смена root/store/host, навигация, close, несколько окон и pending HTML обрабатываются отдельно. canWrite повторно проверяет GM, совместимость, систему и те же DOM-узлы перед действием. Уже подтверждённая scoped запись может закончиться после смены контекста/close, но callback не обновляет снятую панель и не затрагивает другую систему.

Вкладка доступна GM после readiness/compatibility guard во всех системах с выбранной системой, независимо от resolutionMode. Панель из Crafting Settings удалена. Это доступность справочника; свойства по-прежнему не применяются при крафте.

## UI

Структура повторяет VocabularyPanel: описание, блок name/description и «Добавить», строка поиска/количества, карточки со стандартным тегом, названием, меткой использования и удалением. Минимальное прежнее редактирование сохранено через кнопку карандаша и явное сохранение. Используются штатные manager-vocabulary/manager-field/manager-button классы; собственные стили ограничены скрытием, fieldset и эквивалентом scoped neutral Chip. Нет выбора или хранения иконок.

Поиск отключён с понятной подписью «Поиск пока недоступен». Количество берётся из текущего каталога; использование не рассчитывается и не выдаётся за ноль/Unused. Удаление всегда требует отдельного подтверждения в карточке. Pending блокирует повторные действия, ошибка сохраняет ввод/подтверждение для повтора. Пользовательские названия, описания и ошибки выводятся textContent/value без HTML enrichment. Перечитывание/смена вкладки или контекста сбрасывает несохранённый ввод. Автоматической подписки на сохранение другого GM нет: использовать «Перечитать справочник».
