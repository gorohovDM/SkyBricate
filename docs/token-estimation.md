# Оценка расхода токенов следующих этапов

Дата исходной калибровки: 19 октября 2026 года. Пользователь попросил сохранять расчёты и приблизительные оценки в передаче следующих этапов. Это методика планирования, не ограничение бюджета и не разрешение начинать работу.

## Подтверждённый ориентир

Этап 4: **около 7,5 млн токенов** по счётчику пользователя. Пользователь подтвердил изолированное измерение: других задач одновременно не выполнял. Детали результата и границы проверки — в [передаче этапа 4](stage-4-editor-contract.md).

Известно одно наблюдение. Нет разбивки по агентам, входу, кешу, выходу и количеству обращений. Поэтому пока нельзя установить фактическую эффективность, стоимость или статистически надёжный прогноз. Оценка агента 40–70 тыс. суммарных токенов для этапа 4 отозвана как ошибочная.

## Расчёт

Для каждого агента a и обращения i:

`T ≈ Σ_a Σ_i (I[a,i] + O[a,i])`

Грубое приближение для планирования:

`T ≈ Σ_a (N[a] × средний входной контекст[a] + суммарный выход[a])`

Здесь N — количество обращений к модели, I — вход, O — выход, включая учитываемое метрикой рассуждение. Повторно поданный контекст учитывается повторно. Если cached input является частью input, не прибавлять его второй раз; аналогично не прибавлять reasoning второй раз, если он уже входит в output. При анализе накопительных счётчиков брать приращения/итог, а не складывать все накопительные значения. Проверить, включает ли родительский счётчик дочерних агентов, чтобы не посчитать их дважды.

Иллюстрация, не реконструкция этапа 4: 75 обращений со средним входом 100 тыс. токенов дают 7,5 млн входных токенов ещё до добавления выхода. Реальные N и средний контекст этапа 4 не измерены.

## Предварительные оценки до накопления статистики

Диапазоны ниже — эвристические допущения относительно одного ориентира 7,5 млн, а не измеренные коэффициенты или обещание верхней границы. Предполагается тот же процесс analyst → executor → reviewer и тот же способ учёта. Назначать конкретному этапу диапазон только после чтения его требований; номера этапов сами по себе сложность не определяют.

| Характер задачи | Оптимистично | Основной ориентир | С запасом |
| --- | ---: | ---: | ---: |
| Уже изученный контракт, локальные изменения, мало новых сценариев | 1,5 млн (0,2×) | 3 млн (0,4×) | 5,25 млн (0,7×) |
| Сопоставимо с этапом 4: UI/адаптер, асинхронность, контрактные тесты | 4,5 млн (0,6×) | 7,5 млн (1×) | 11,25 млн (1,5×) |
| Сложнее этапа 4: несколько путей интеграции, delayed/multistep, дополнительное исследование | 7,5 млн (1×) | 11,25 млн (1,5×) | 18,75 млн (2,5×) |

Значения вычислены умножением 7,5 млн на указанные условные коэффициенты. Дробные значения не означают такую точность прогноза. Повторные исправления, неожиданная несовместимость и увеличение контекста могут вывести расход за диапазон.

При выборе диапазона учитывать объём чтения, число независимых изменений, неизвестные API, асинхронные сценарии, необходимые проверки, размер diff и риск повторного ревью. Дополнительно учитывать полную передачу истории агентам, повторное чтение и частоту обращений координатора. Не объявлять эти факторы доказанной причиной фактического расхода без анализа журналов.

## Что переносить в каждый следующий файл передачи

1. До реализации: границы разрешённого этапа, класс сложности, три оценки в миллионах суммарных токенов, допущения и основные источники неопределённости.
2. После завершения: факт по тому же счётчику пользователя или проверенным журналам. Если факт неизвестен, написать «не измерен», не выдавать оценку за измерение.
3. По возможности: вход, кешированная часть входа, выход, число обращений и распределение между агентами с описанием правил суммирования.
4. Сравнение факта с основным прогнозом: `факт / прогноз`; объяснять отклонения только подтверждёнными наблюдениями.
5. Ссылка на этот документ и предыдущую передачу. Обновлять ориентиры по мере накопления сопоставимых завершённых задач; не выводить постоянный множитель из ошибочной оценки 40–70 тыс.

Стоимость и лимиты подписки оценивать отдельно: суммарные токены разных категорий не следует считать одинаковыми по цене или автоматически переводить в процент лимита.
