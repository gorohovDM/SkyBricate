# Этап 9а: данные штатной попытки до расхода

Реализована часть 9а плана от 20 октября 2026 года. База: `origin/main` `354f565b498093f42123a697cc77d8bc1b3dcdc3`, предыдущий `origin/codex/dev` `0748c2293bc93c001b7ada3dfdc2bfb28c4f11de`. Проверяемый stock Fabricate 1.9.10: `5bf36ddf950619317e41737acd3bfa1305591a26`. Сторонние исходники читаются из этого коммита и не изменяются.

## Конфигурация связи

Пользователь выбрал явную связь свойства SkyBricate с эссенцией текущей системы Fabricate: используются её эффекты и property macro. Поле `systems[systemId].properties[propertyId].essenceId` необязательно; ID не выводится из имени или propertyId. Связь хранится только в SkyBricate. Назначения компонентам не копируются в native essences, Workbench или inventory.

GM выбирает эссенцию в форме каталога «Свойства»; название сопровождается ID. Пустой выбор снимает связь. Удалённая эссенция показывается как отсутствующая, чтобы GM мог заменить или снять связь. Переименование свойства сохраняет link. API DataStore `createProperty`/`updateProperty` принимает `essenceId`; `null` снимает link при обновлении. Запись сверяет ID с сохранёнными эссенциями текущей системы; существующую отсутствующую связь можно оставить при обычном API-переименовании, но выбранное свойство с такой связью не пройдёт craft preflight.

Для однозначного происхождения и запрета двойного будущего применения одна эссенция может быть связана только с одним свойством внутри системы. Повтор отвергается до записи; одинаковый essenceId в разных системах независим. Свойство без связи допускается в каталоге и назначениях; проверка крафта требует связь только для свойств, которые реально могут попасть в выбранный набор этой попытки.

Схема 6 отличается от схемы 5 необязательным `essenceId`. Строго корректные схемы 2–5 читаются без записи; при следующей успешной записи сохраняется схема 6. Сохраняются каталоги, типы назначений, знания и правила рецептов схемы 5. Неизвестные поля старых схем, повреждённые данные и будущие версии отвергаются. Старые описания схем в прочих документах являются историческими.

## Штатный маршрут и состав

После `fabricate.whenReady()` адаптер подключается к экземпляру `getCraftingEngine()`. Версия проверяется существующим lifecycle. Захватываются существующие `craft` и `craftAlchemy`, включая ранее установленные обёртки; при снятии адаптера чужая более поздняя обёртка не перезаписывается.

Для каждой настроенной попытки создаётся отдельный receiver `Object.create(engine)`, с локальными перехватами `_resolveCraftSelection` и `_runCraftingCheck`. Реальные менеджеры и native методы остаются общими сервисами Fabricate; изменяемой переменной «текущий крафт» на engine или глобальном объекте нет. Обёртки, использующие правильный динамический `this`, сохраняются; сторонние обёртки, жёстко привязанные к исходному engine или самостоятельно меняющие порядок расхода, этим контрактом не покрываются.

`_resolveCraftSelection` вызывается штатным `craft` один раз. Адаптер читает возвращённый native plan, не вычисляет повторно распределение ингредиентов и не расходует их сам. Снимок содержит `itemUuid`, `actorUuid`, `componentId`, `quantity`, `kind` (`ingredient`/`extra`) до удаления или изменения Item. Количество экземпляров одного componentId не превращается в несколько различных компонентов для алгоритма 7. Инструменты и currencySpends не становятся компонентами: их участие/расход оставлены Fabricate.

Для обычного крафта componentId определяется штатным `RecipeManager.ingredientMatchesItem` по конкретным component refs текущей системы. Это сохраняет stock identity/source/name правила без собственного парсера UUID или реконструкции по имени удалённого Item. Несколько подходящих componentId считаются неподдержанной неоднозначностью и прерывают попытку до броска/расхода; Item без managed component имеет `componentId: null` и не добавляет кандидатов.

Алхимия сохраняет исходные bucketed `{item, componentId}` из `craftAlchemy`; повторного определения ID по имени/Item после расхода нет. Матчинг и выбор рецепта остаются штатными. Extras вычисляются ровно по правилу stock `_consumeAlchemyExtraItems`: считаются повторные UUID в `alchemySubmittedItems`, кроме UUID, уже затронутых основным планом. Если основной план потребляет одну единицу стека, дополнительные submitted единицы того же UUID не являются extras. Это особенность stock 1.9.10, адаптер её не исправляет.

Состав — снимок плана участия перед расходом, а не подтверждение выполненного расхода. Штатная failure policy может не расходовать ингредиенты или extras; такой исход не считается применением. Сопоставление с реально переданным `consumedItems` и успешной выдачей результата обязательно для этапа 9б.

## Проверка и выбранный набор

Настройки SkyBricate и нужная конфигурация Fabricate копируются для одной попытки. До native `craft` проверяется поддерживаемый контекст и полнота лимитов по текущим стабильным исходам. После получения native plan, до вызова native проверки валидируется объединение наборов, возможных при настроенных исходах: связь с единственной включённой эссенцией, доступный script macro с непустым command и/или источник эффектов при включённых native gates. UUID разрешаются, но макросы на preflight не исполняются. Удалённый source Item/неразрешимый macro отвергается. Незаполненные свойства вне подходящего набора и свойства за нулевым лимитом не блокируют крафт.

Ошибки этой статической конфигурации останавливают попытку до броска и расхода. `_runCraftingCheck` вызывается ровно один раз; его оригинальный результат сохраняется. Для simple берутся только stock `pass`/`fail`; для routed/tiered — `checkResult.data.outcomeId`, display name `outcome` не используется как ID. При отсутствии броска и выключенном лимите outcomeId равен `null`. При включённом лимите неизвестный/отсутствующий фактический исход останавливает попытку после единственного броска, до расхода. Отмена и native `misconfigured` возвращаются без выбора/расхода.

Алгоритм 7 вызывается с правилами конкретного рецепта этапа 8. Отсутствие правил сохраняет поведение 7; сохранённый пустой allowlist запрещает все свойства. Снимок выбранных записей сохраняет `propertyId`, `selectionType`, `sources[{componentId,assignmentType}]` и `essenceId`. Проверка может быть неуспешной: наличие снимка не утверждает успех или применение свойства.

Контекст хранится в закрытой module WeakMap, доступной внутреннему `getCraftAttempt(receiver)` только на время native вызова; функция возвращает копию. После завершения/исключения запись удаляется. Снимки не публикуются в module.api, Item flags, run, hooks, chat или player DOM. Записи знаний не выполняются. Для игрока ошибки не содержат скрытых property IDs/названий; GM получает техническую причину в console. World setting по-прежнему доступен клиентскому JS: серверная секретность не заявлена.

Без назначений SkyBricate и без правил текущего рецепта обычный `craft` проходит через исходный метод с исходным receiver. No-match алхимии остаётся штатным, с прежней политикой расхода и без броска. Настроенные delayed, multistep (включая collapsed chain), progressive и уже подготовленные timed runs безопасно отклоняются до входа в native craft; это граница 9в. Прямой настроенный `craft` с флагами алхимии без bucketed `craftAlchemy`-контекста отвергается до броска/расхода.

## Проверенные точки будущего применения 9б

Stock `_runPropertyMacro` сам по себе недостаточен: essence macros исполняются раньше, effect transfer — после native создания Item. Проверен следующий будущий контракт без реализации применения в runtime 9а:

1. Один attempt-local `precomputedEssences` с ID выбранных связанных эссенций передаётся обоим stock путям `_runEssencePropertyMacros` и `_transferEffects`. Для этой попытки ни один из путей не получает несвязанный или отсечённый набор SkyBricate через обычное накопление эссенций компонентов.
2. Для essence macro передаётся локальная копия `system` с `essenceDefinitions` в порядке выбранных свойств. Исходная библиотека и `definition.enabled` не изменяются. Native macro runner получает штатный context; собственный result property macro сохраняет штатную позицию последнего writer.
3. Effect transfer итерирует ключи того же `precomputedEssences` в порядке вставки; enabled map ограничен попыткой. Native feature gates (`essences`, `propertyMacros`, `effectTransfer`, `recipe.transferEffects`) сохраняются.
4. Native создание/stacking остаётся штатным. До включения 9б нужны отдельные проверки чужого result macro, коллизий путей/эффектов, veto stacking, фактической выдачи и аудита реально применившихся свойств. 9а этого не реализует и не объявляет свойства применёнными. Независимые native essences пока работают по прежним правилам Fabricate; лимит SkyBricate пока ограничивает только снимок выбора.

Значение `essenceQuantity` для выбранного свойства не определяется этапом 9а: применение один раз и суммирование количеств источников дают разное поведение макросов. Следующее задание 9б должно явно определить эту семантику; все исходные количества сохранены. Stock probe доказывает прохождение произвольного переданного количества по обоим швам, не закрепляя продуктовое правило.

## Автоматическая проверка

`node --test tests/regression.test.mjs` — полный suite, включая миграцию 5→6, CRUD/GM selector, limits, privacy, concurrent attempts, ошибки macro/source и конфигурации до roll/расхода. `node tools/build.mjs` проверяет упаковку runtime allowlist; документы, тесты, tools и `.reference` исключены.

Новый `node tools/check-fabricate-craft.mjs [path]` исполняет настоящие CraftingEngine, RecipeManager, Recipe, IngredientSet, ResolutionModeService и checkRoll из pinned commit. Проверяет standard/alchemy success, failure results, interactive cancel, no-match, none/simple/tiered check, реальный outcomeId, один native selection/roll/consume, partial/full stack, одинаковые componentId, bucketed extras/UUID exclusion и preflight. Отдельно исполняет настоящие essence property macros и effect transfer на одном ограниченном precomputed map как доказательство будущих точек подключения. Копии исходников probe создаются только в собственном cache и удаляются после выполнения.

Дополнительно сохранены stock probes редактора, назначений, player provider и правил рецепта. Настоящий Foundry, перезапуск мира, реальные документы/диалоги других модулей и произвольные сторонние обёртки не проверялись; ручной Foundry исключён из задания. Работа этапов 9б, 9в и 10 не начиналась.
