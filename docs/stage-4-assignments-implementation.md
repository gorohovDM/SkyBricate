## Проверенный контракт

`game.fabricate.getCraftingSystemManager().componentAssignmentContract` возвращает объект:

```js
{
  version: 'fabricate-component-assignments-v1',
  deletedHook: 'fabricate.componentsDeleted',
  readPersistedSystem(systemId) { /* synchronous full saved snapshot */ }
}
```

Чтение возвращает `{ systemId, complete: true, componentIds: [...] }`. Источник — весь сохранённый `fabricate.craftingSystems`, а не mutable manager map, список интерфейса, фильтр или проекция store. Неизвестная система, неполные данные, дубли и ошибка чтения приводят к отказу; SkyBricate дополнительно проверяет IDs и контракт. Существующая система с сохранённым пустым `components: []` допустима. Отсутствие целой системы не трактуется как пустая система и не запускает очистку.

Форма `form#manager-component-edit-form.manager-component-edit-view` предоставляет `data-crafting-system-id` и `data-component-id` из `selectedSystem.id` и фактического `componentForEdit.id`. Оба атрибута отсутствуют при неполной паре. Переходы и native dirty guards сохраняются. Отмена перехода оставляет прежнюю пару; закрытие/смена экрана снимает форму и панель. Имена и совпадение полей не используются.

Hook `fabricate.componentsDeleted` доставляет `{ systemId, componentIds }` через стандартный `Hooks.callAll` после fulfilled сохранения общего `SettingsCraftingDefinitionRepository._write`. Он сравнивает полный корпус до и после записи; одиночное `deleteItem`, массовое `deleteComponents`, прямое сохранение и repository batch используют один путь. Пустой результат, отмена или rejected persistence не дают успешного уведомления. Исключение notification consumer не отменяет уже сохранённую запись. Удаление целой системы этим событием не обрабатывается.

SkyBricate подписывается один раз на срок жизни установленного адаптера, а не на каждый render/окно; dispose снимает hook. Закрытие окна снимает его observer, store subscriptions и локальные обработчики, но глобальная обработка удалений продолжает работать. Полученные IDs сверяются повторно с полным persisted состоянием в очереди DataStore: существующие компоненты не удаляются из назначений даже при повторной/устаревшей доставке. Общая сверка текущей системы удаляет только назначения отсутствующих компонентов. Ошибка очистки показывает предупреждение и сохраняет список затронутых систем для повторной сверки. Два хранилища не атомарны; при пропущенном событии или перезагрузке мастер запускает сверку снова.

## Поведение и проверки

Панель монтируется рядом с native тегами, сохраняет только собственные свойства компонента отдельной кнопкой и не меняет штатные tags/essences/category. Есть пустое состояние, перечитывание, pending, повтор после ошибки и заранее видимое пояснение о сбросе выбора при навигации. Системные/компонентные ID, GM, существование компонента и текущий DOM проверяются до действия и при исполнении queued записи; свойства проверяет схема DataStore. Уже начатая запись сохраняет исходную пару и не обновляет чужую/снятую панель. Успех показывается только после fulfilled записи. Категории и прежние данные назначений не смешиваются и не мигрируются.

Результаты:

- `node --test tests/regression.test.mjs`: 52/52 PASS. Каталоги/компоненты изолированы, пустые назначения и каталог, безопасные строки, ошибочный контракт, очередь/GM/удалённый компонент, stale actions, close/rerender, два окна, rejected cleanup, повторная доставка и безопасная полная сверка.
- `node --conditions=browser tools/check-fabricate-editor.mjs`: PASS, реальные TagsCategoriesView/VocabularyPanel, native формы/вкладки, клавиатура/ARIA, lifecycle.
- `node --conditions=browser tools/check-fabricate-assignments.mjs`: PASS, реально скомпилированные CraftingSystemManagerRoot/ComponentEditView, два одинаковых по полям компонента с разными ID, native tag draft, отменённый/принятый переход, native сохранение категории, переименование, remount/close; оригинальный unpatched ComponentEditView блокирует назначения с пояснением.
- Тот же probe: реальный adminStore с отменой удаления; реальные `deleteItem`/`deleteComponents` и общий repository batch; rejected persistence не уведомляет; успешное удаление с rejected cleanup сохраняет данные Fabricate и показывает рассинхронизацию; повторная сверка исправляет её. Новый DataStore восстанавливает состояние после пропущенного события/условной перезагрузки клиента.
- Обе сборки PASS. Fabricate: Vite 725 модулей, штатная валидация dist и manager chunk split; отдельно подтверждена полнота chunks готового собственного ZIP. Есть предупреждение upstream о deprecated `inlineDynamicImports`; сборка завершилась успешно.

Первая техническая отсечка пройдена на реальном manager/editor в тестовом DOM; блокер идентичности устранён согласованным расширением. Проверки DOM не заменяют работу в мире Foundry. Не проверены запуск/перезапуск настоящего мира, визуальные темы, узкая ширина, реальные Foundry диалоги и несколько реальных клиентов. Ручной smoke остаётся отдельной эксплуатационной проверкой. Независимое ревью опубликованного SHA, итоговое дерево test и подтверждённый push test — задача reviewer.

Модель нескольких GM остаётся «последняя запись побеждает» с явным перечитыванием. Межклиентская блокировка, назначения категориям, наследование, Actor/знания, интерфейс игрока и применение свойств при крафте не начинались.

## Расход

Класс: сложная интеграция. Предварительный эвристический прогноз полного цикла: 7,5 / 11,25 / 18,75 млн суммарных токенов (оптимистично / основной / с запасом). Это не бюджет и не потолок. Исключение категорий снижает объём; persisted contract, доставка Fabricate, реальные Svelte-компоненты и независимое ревью добавляют неопределённость. Фактический расход по пользовательскому счётчику не измерен; сравнение с прогнозом пока невозможно. Исходные пользовательские правки `stage-4-scoped-properties-contract.md` и `token-estimation.md` сохранены без включения в commit задачи.
