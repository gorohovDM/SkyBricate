# Этап 9б: применение свойств к выданному Item

Реализован immediate single-step крафт обычного Fabricate 1.9.10, pinned commit `5bf36ddf950619317e41737acd3bfa1305591a26`. Базовая ветка `origin/main` — `354f565b498093f42123a697cc77d8bc1b3dcdc3`, исходный `codex/dev` — `080957272d0326701dde922e0735685454ba16a4`. Сторонние исходники не меняются. Это продолжение [9а](stage-9a-craft-adapter.md); delayed/multistep/progressive (9в) и автоматическое раскрытие знаний (10) не реализованы.

## Сила по исходу проверки

Прямое решение пользователя: силу выбранного свойства определяет исход единственной штатной проверки; GM задаёт её в правилах сохранённого рецепта. Без проверки сила каждого свойства всегда 1 и не зависит от количества ингредиентов.

В окне «Правила рецепта SkyBricate» у каждого стабильного native outcome ID отдельное поле силы. Оно активно и при выключенном лимите количества свойств. `outcomeLimits` определяет число разных выбранных свойств; необязательная карта `outcomeStrengths` задаёт одинаковый `essenceQuantity` каждому свойству выбранного набора при данном исходе. Допустимо любое положительное конечное JS Number, включая дробное; ноль, отрицательные значения, строки, NaN и Infinity запрещены. Это множитель/аргумент макроса, а не дополнительное количество расходуемых ингредиентов. Штатные ActiveEffects копируются один раз, их changes не умножаются автоматически: stock transfer не использует количество эссенции для изменения эффектов.

Отсутствующая карта совместимо означает силу 1. При наличии карты она должна точно покрывать текущие исходы, даже если лимит количества выключен. Для режима без проверки допустима только пустая карта или отсутствие карты, сила всегда 1. Неизвестный фактический исход при доступной проверке останавливает попытку после единственного броска, до расхода, в том числе при отсутствии карты. Display name не заменяет ID tier. Смена исходов требует перечитывания/коррекции карты. Контекст и права GM перепроверяются в очереди сохранения, как в этапе 8; штатный рецепт сначала создаётся/сохраняется Fabricate, правила сохраняются отдельно.

Схема 7 добавляет только необязательное поле правил рецепта `outcomeStrengths`. Строго корректные схемы 2–6 читаются без записи и без добавления отсутствующих карт; первая успешная запись сохраняет схему 7. Неизвестные поля старых схем и будущие версии отвергаются. Имена/ID свойств, связи с эссенциями, назначения и знания сохраняются.

## Штатное применение и порядок

Каждый native craft имеет отдельный receiver этапа 9а, каждый результирующий Item — отдельный дочерний receiver. `craft-application.js` оборачивает существующие узкие seams, не копирует `_createSingleResult`, не меняет singleton engine, actor methods, библиотеку или глобальные `enabled`. Изменения не попадают в следующий результат/параллельную попытку. Бросок, потребление и создание остаются штатными и не повторяются.

Для каждого результата состав этапа 9а сопоставляется с реально переданным ему `consumedItems` по UUID и положительному фактическому количеству в границах плана. Неизвестные/избыточные расходы не добавляют источников. Повторные строки одного UUID агрегируются. Выбранное обычное свойство остаётся eligible только при двух реально потреблённых componentId из его исходных источников; особое — при хотя бы одном исходном особом источнике. Обычные источники того же propertyId не подмешиваются к особому. Потеря источника не заполняет освободившееся место другим свойством за лимитом. План не подменяет фактический расход: native failure policy с отсутствием расхода даёт отсутствие Sky-применения. Алхимические extras и удалённые/частичные стеки подтверждаются тем же UUID из снимка до расхода.

Общий ограниченный essence context используется essence macros, result macro и transfer effects. Все эссенции, связанные с любым свойством текущего каталога SkyBricate, удаляются из native накопления и возвращаются только для eligible выбранного свойства с заданной силой. Так ингредиент с native essence не обходит allowlist/лимит, и одна связанная эссенция не применяется дважды.

Независимые native essences сохраняются вне лимита SkyBricate, со штатными количествами, source metadata и disabled-поведением. Их macros выполняются первыми в native library order, затем выбранные Sky-свойства в порядке выбора, затем собственный result macro остаётся штатным последним writer. Эффекты независимых эссенций идут в прежнем порядке накопления native map, затем Sky в порядке выбора. Локальное представление context сохраняет этот порядок также для числовых essence IDs. `_transferEffects` сохраняет один штатный create batch, включая поведение ошибки разрешения позднего источника; промежуточных отдельных партий нет.

Native gates `essences`, `propertyMacros`, `effectTransfer`, `recipe.transferEffects` сохраняются. Эффекты копируются после native создания Item. Для eligible непустого Sky-набора включается stacking veto, включая effect-only/no-op: иначе native merge отбрасывает индивидуальные данные/audit. Сам veto не считается применением. При пустом eligible наборе сохраняется native stacking, собственный аудит для этого award не добавляется.

## Подтверждение фактического применения

`flags.skybricate.application` записывается после возврата всей native попытки только на Item из её возвращённого `results`, который по-прежнему находится в inventory Actor. Запись содержит version, system/recipe/result ID, actor UUID, outcome ID, силу, `checkSuccess`, `craftSuccess` и `applied`. У каждого applied-свойства есть propertyId, essenceId, selectionType, outcomeId, strength, признаки macro/effects и только фактически потреблённые исходные sources с componentId, assignmentType, Item/Actor UUID, quantity и kind. Названия, описания, невыбранные свойства и весь набор кандидатов в аудит не копируются. Копия старого audit с зарегистрированного source Item удаляется при подготовке нового результата.

Макрос считается применившимся только при сохранившемся изменении значения `system.*` относительно исходных данных результата, наблюдавшемся при его штатном применении. Пустой/null/ошибочный macro, одинаковая запись и изменения, удалённые нормализацией Item, не засчитываются. Поздняя запись в тот же путь/родителя/потомка снимает прежнюю атрибуцию, даже при одинаковом значении. При partial path error учитываются только реально изменённые и сохранившиеся значения; все объявленные конфликтующие пути консервативно снимают предыдущую атрибуцию. Восстановление исходного значения не считается изменением. Изменения только имени/картинки, произвольных flags, удалений без сохранившихся значений или внешние побочные действия не дают macro-applied. Это намеренно консервативная атрибуция: наличие макроса само по себе не доказывает применение.

Эффект подтверждается только фактически созданным embedded Document с ID, оставшимся на выданном Item, с активными changes/statuses. Перед native transfer источники дополнительно читаются для наблюдения шаблонов. Ownership признаётся только если фактическая партия совпадает с наблюдёнными шаблонами и созданные документы соответствуют им. Если шаблоны поменялись между чтениями, attribution пропускается. Эффекты с одинаковыми changes/statuses, включая уже имевшиеся на source результате и независимые native эссенции, неоднозначны и не дают applied по effects; сами эффекты stock не удаляются и не дедуплицируются. Disabled/пустые, не созданные или не сохранившиеся эффекты не засчитываются. Доказанного macro-изменения достаточно и при неоднозначных эффектах, и наоборот.

После исключения native creation/effects/chat или swallowed failure-award exception завершённый audit не записывается, в том числе на ранее частично созданный результат. Failure-result допускается с `checkSuccess: false`; будущий этап 10 обязан проверять успех и не раскрывать знания по нему. Аудит не является системой отката: расход, уже созданные Item/effects и произвольные macro side effects при исключении остаются по native правилам. Ошибка записи flags также не откатывает выданный Item. Одновременная ручная/сторонняя модификация документа между проверкой и записью flags не образует транзакцию.

Скрытые названия не добавляются в UI/chat. Как и ранее, world setting и Item flags доступны разрешённому клиентскому JS; серверная секретность не заявляется. Произвольный авторский macro сам отвечает за свои сообщения и побочные действия. Знания SkyBricate не записываются.
