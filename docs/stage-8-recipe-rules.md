# Этап 8: правила свойств конкретного рецепта

Реализованный контракт от 20 октября 2026 года. База main: `354f565b498093f42123a697cc77d8bc1b3dcdc3`; предыдущая реализация этапа 7: `899b0d081d1a592a1eb1f6e4ed724040ed190030`. Документ уточняет исторический контракт этапа 7: для настроенного рецепта список ограничивает разрешённые свойства, а не только сортирует кандидатов. Это решение пользователя принято после предварительной оценки этапа 8.

## Интерфейс GM и интеграция

Используется штатный Fabricate 1.9.10, commit `5bf36ddf950619317e41737acd3bfa1305591a26`, без патча и отдельной сборки. В библиотеке рецептов GM рядом с карандашом каждой строки появляется кнопка с ползунками «Правила рецепта SkyBricate». Она открывает окно настроек ровно этого сохранённого рецепта; система и рецепт зафиксированы, имя и ID показаны в заголовке. Выбор рецепта повторно не требуется.

Точки идентификации: `_adminStore.selectedSystemId` вместе с совпадающим `viewState.selectedSystem.id`, затем `.manager-recipe-row[data-recipe-id]` и единственная штатная `button.manager-recipe-edit[data-recipe-edit]` с тем же ID. ID дополнительно сверяется с полными сохранёнными `fabricate.craftingSystems` и `fabricate.recipes`, world settings типа Array. Структура и версия проверяются; неоднозначные строки, несовпадение системы и неизвестный формат блокируют действие. Смена системы навсегда инвалидирует контекст уже открытого из этого менеджера окна; его надо открыть заново. Закрытие/замена менеджера, удаление рецепта и потеря GM-прав также блокируют запись.

Почему кнопка находится в библиотеке: штатный `CraftingSystemManagerRoot.svelte` хранит `selectedRecipeId` и черновик редактора внутри Svelte-компонента, не публикуя ID в admin store или DOM `RecipeEditView`. Привязка по текстовому имени неоднозначна. Строка библиотеки публикует точный ID и допускает связанное окно без вмешательства в приватные внутренности Svelte. Создание рецепта остаётся штатным: native `createRecipe` сразу сохраняет выключенную заготовку с постоянным ID. Для её настройки нужно вернуться в библиотеку рецептов и нажать кнопку в строке.

В окне GM добавляет свойства из справочника выбранной системы, меняет их последовательность кнопками «Выше»/«Ниже», убирает строки, задаёт приоритет особых назначений и лимиты по штатным исходам. Повторный выбор свойства исключён. Подписи, имена и описания выводятся текстом. Пустой список явно поясняется: после сохранения он запрещает все свойства. До первого сохранения показано, что действует прежний выбор.

Кнопка «Сохранить правила рецепта» пишет только SkyBricate. Несохранённые штатные изменения рецепта не включаются. Сохранение, отмена, dirty guards и навигация Fabricate не подменяются. Закрытие нашего окна отменяет только его несохранённые правки; повторный render ApplicationV2 сохраняет их. «Перечитать сохранённые правила» явно отменяет наш черновик и читает актуальные данные. После изменений сохранённого рецепта/проверки или правил в другом окне сохранение отклоняется с предложением перечитать данные.

## Хранение и выбор

Схема 5 добавляет `systems[craftingSystemId].recipeRules[recipeId]`:

```js
{
  allowedPropertyIds: ["property-a", "property-b"],
  propertyOrder: ["property-b", "property-a"],
  limitByCheck: false,
  outcomeLimits: { fail: 0, pass: 2 },
  prioritySpecial: false
}
```

Оба списка состоят из уникальных ID каталога системы; порядок может включать только разрешённые ID. UI записывает один выбранный список в оба поля в заданной последовательности. API допускает часть разрешённых ID вне `propertyOrder`; они сортируются по ID после упорядоченных. Обе опции по умолчанию выключены. Лимиты — целые неотрицательные safe integers, включая 0.

`selectProperties` принимает необязательный `recipeRules.allowedPropertyIds`: отсутствие поля сохраняет контракт этапа 7; присутствующий пустой массив запрещает всё. Фильтр применяется к кандидатам до общего лимита и после проверки входных данных. Список не создаёт свойство без назначений участвующим компонентам. При включённом приоритете особые кандидаты внутри разрешённого набора идут первыми; их обычные источники не подмешиваются. Общий лимит считает различные propertyId. Знания персонажей и видимость особого раздела не участвуют.

Сохранённое отсутствие `recipeRules[recipeId]` означает, что новых настроек нет: оно не превращается автоматически в пустой запрет. Старые системные `rules` не копируются в рецепты и продолжают храниться без изменений. Пример подготовки для API этапа 9:

```js
const snapshot = api.data.getSnapshot();
const system = snapshot.systems[systemId];
const selected = api.selectProperties({
  system, componentIds,
  recipeRules: system.recipeRules[recipeId] ?? {},
  outcome // pass/fail для простой проверки; checkResult.data.outcomeId для tiered
});
```

Корректные схемы 2/3/4 читаются без записи и обновляются до 5 только при успешной мутации. Каталоги, обычные/особые назначения, существующие правила и знания схемы 4 сохраняются. Схема 1 остаётся только на явном сбросе; повреждённые данные и будущие схемы не нормализуются и не сбрасываются. Переименование сохраняет ID; удаление свойства одним сохранением очищает назначения, знания, системный порядок и оба списка всех рецептов этой системы.

Новые операции DataStore: `configureRecipeRules(systemId, recipeId, fullRules, options)` и `reconcileRecipeRules(options)`. Проверки GM, актуального сохранённого рецепта и его системы выполняются внутри очереди на свежем snapshot. UI передаёт `canWrite`, `expectedRules` и `expectedContext`: устаревшее окно не перетирает более новые правила, удалённое свойство или изменившийся рецепт/проверку. Опции expected необязательны для прямого GM API. Ошибка сохранения не меняет persisted данные и не ломает очередь.

После успешного обновления native settings GM-клиент сверяет полную базу и удаляет правила исчезнувших/перенесённых рецептов; неуспешная native запись не вызывает очистки. Ошибка чтения/формата блокирует её. При закрытом менеджере обработчик продолжает действовать после готовности модуля. Удаления, произошедшие при выключенном SkyBricate, можно сверить через `api.data.reconcileRecipeRules()`; их старые записи сами по себе не дают доступа к несуществующему рецепту. Копирование native рецепта/системы создаёт новые ID: правила SkyBricate не копируются и не наследуются. Новую копию GM настраивает явно. Импорт с намеренным повторным использованием прежних ID считается восстановлением той же идентичности; отдельного поколения/истории ID нет.

## Исходы штатной проверки

| Режим | Ключи лимитов |
| --- | --- |
| simple с включённой проверкой и пригодной формулой | `fail`, `pass` |
| routedByIngredients с пригодной simple-формулой | `fail`, `pass`, независимо от master toggle |
| alchemy / simple | `fail`, `pass` при пригодной simple-формуле |
| routedByCheck или alchemy / tiered | ID активных `craftingCheck.routed.relativeOutcomes` либо `fixedOutcomes` по `type` |
| alchemy / none, выключенная/непригодная optional проверка, progressive | нет дискретных исходов: включение лимита запрещено |

В simple учтены оба штатных gate: `features.craftingChecks` или `craftingCheck.enabled`. Пустые формулы не считаются проверкой. Формулы со старым `@craftingmod` консервативно блокируют настройку лимита до их исправления/миграции в Fabricate: его сложный retirement parser в модуль не копируется. Неизвестный mode/type, отсутствующие или повторные ID градаций блокируют контекст.

`runFormulaPassFail` возвращает `outcome: 'pass'|'fail'`. Штатный routed runner возвращает отображаемое имя в `outcome`, а постоянный ID в `data.outcomeId`. Настройки привязаны к ID: переименование не теряет лимит. Этап 9 обязан передавать именно этот ID и явно обрабатывать null/unmapped outcome. При включённом лимите сохранение требует количество для каждого текущего исхода и не допускает посторонние ключи. UI предлагает 0 для ещё не настроенного исхода; запись происходит только по действию GM. При смене native mode/проверки открытое окно требует перечитывания. Inactive/удалённые исходы UI не переносит в новую запись; при выключенном лимите хранилище допускает числовые значения без проверки актуального набора.

Предварительная оценка 4 / 6 / 9 млн токенов относилась к отдельному сохранению до подтверждения ограничивающего списка. Allowlist расширил согласованный объём. Фактический расход токенов этим документом не измеряется и не утверждается.
