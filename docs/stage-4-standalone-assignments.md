# Этап 4: самостоятельный редактор назначений

Это актуальная передача переделки этапа 4 от 19.10.2026. Она заменяет интеграцию назначений из `stage-4-assignments-implementation.md` и `stage-4-scoped-properties-contract.md`: патч и собственная сборка Fabricate больше не используются. Исторические документы и чужие локальные правки, включая фактические 12,87 млн токенов прошлой задачи, сохранены. Дальнейшие этапы не реализованы.

База: актуальный `origin/main` `354f565b498093f42123a697cc77d8bc1b3dcdc3`, включённый в `codex/dev`; предыдущий опубликованный dev `0bf9e9ebaf41dbe9b90d5301e465a1fe41c3e0aa`. Ветка для проверки — `origin/codex/dev`. Интеграцию в `test` выполняет ревьюер после независимой проверки; исполнитель публикует только dev.

## Поведение и критерии приёмки

- Мастер открывает «Настроить параметры» → SkyBricate → «Открыть редактор назначений». Это отдельный ApplicationV2 с restricted settings menu; доступ также через `game.modules.get('skybricate').api.openAssignments()`. Readiness, совместимость и GM проверяются повторно; очередь данных проверяет полномочия при исполнении операции.
- Системы и компоненты берутся только из сохранённого полного setting Fabricate. Выбор не зависит от открытого окна Fabricate, DOM формы компонента или его Svelte-store. Одинаковые имена различаются по ID. Справочник остаётся прежней вкладкой «Теги и категории».
- Плашки показывают собственные свойства выбранного компонента и системы. Сохранение отдельно, снятие всех, перечитывание, пустые состояния и предупреждение о сбросе несохранённого выбора. Ошибка записи сохраняет выбор. Pending блокирует повторное сохранение и навигацию; закрытие отменяет ещё не начатые операции этого окна, отсоединённые кнопки не действуют. Уже начатая запись не откатывается закрытием. Несколько окон независимы, общий DataStore сериализует записи клиента.
- Схема 2 и прежние ID назначений не меняются, миграция не нужна. Переименование и смена категории не затрагивают связь. Назначения категорий не подмешиваются. Неизвестные/повреждённые данные SkyBricate остаются закрытыми для записи.
- Сверка выполняется при открытии, перечитывании и явной кнопкой. Мгновенного уведомления об удалении нет. Каждый queued reconcile повторно читает полный сохранённый корпус; очистка касается только отсутствующих компонентов существующих систем. Явный `components: []` допустим. Отсутствующая система сохраняет назначения; ошибка чтения и malformed корпус не очищают ничего. Отмена удаления и отказ записи Fabricate сохраняют назначения. Пропущенное удаление исправляется повторной сверкой или открытием после перезапуска.
- Runtime ZIP содержит только SkyBricate (12 файлов allowlist), без документации, тестов, стороннего кода и зависимостей разработки. Builder/manifest/patch Fabricate удалены из текущей поставки. Локальный старый Fabricate ZIP и его SHA256 удалены по проверенным точным путям.

## Проверенный контракт Fabricate

Обычный Fabricate 1.9.10, исходный SHA `5bf36ddf950619317e41737acd3bfa1305591a26`: `src/config/settings.js` регистрирует `fabricate.craftingSystems` с `scope: world`, `type: Array`; `getSetting` напрямую читает `game.settings.get`. `SettingsCraftingDefinitionRepository._write` сохраняет полный сериализованный массив систем с компонентами. Адаптер SkyBricate проверяет активность/версию модуля, регистрацию setting, массив, структуру систем и компонентов, безопасные строковые ID, дубли систем и компонента внутри системы. Повторение component ID в разных системах допустимо. Все проверки проходят до удаления назначений; неизвестная версия, неполная запись, отсутствие/отказ setting и неизвестная система отклоняются.

SkyBricate не пишет в Fabricate, не перехватывает его методы и не подписывается на прежние `fabricate.componentsDeleted`/`componentAssignmentContract`. Компонентные UI-проекции не используются как доказательство отсутствия. Тестовые probes читают stock через `git show` указанного SHA, даже если локальная `.reference` содержит старые экспериментальные правки. Они не меняют сторонний checkout и не собирают копию модуля.

- `node --test tests/regression.test.mjs` — 53 теста: справочник, совместимость/readiness, схема и CRUD, standalone DOM, ID/системы, pending/retry, queue/GM/close, независимые окна, испорченный setting, отсутствующие системы, явные пустые списки, повторная сверка, lifecycle settings menu/API и точный воспроизводимый ZIP.
- `node --conditions=browser tools/check-fabricate-editor.mjs` — реальные stock TagsCategoriesView/VocabularyPanel, штатные формы/вкладки и восстановление после закрытия.
- `node --conditions=browser tools/check-fabricate-assignments.mjs` — оригинальные stock manager/repository/adminStore: отменённое и не сохранённое удаление, одиночное и массовое удаление, независимость от хуков, отказ очистки и повтор, сохранение ID после переименования/категории, batch репозитория, изоляция систем, повторное открытие после пропуска удаления.
- `node tools/build.mjs`, `git diff --check`.

ApplicationV2 использует `_renderHTML`, `_replaceHTML`, `_onRender`, `close`, `_onClose` согласно официальной документации [v13](https://foundryvtt.com/api/v13/classes/foundry.applications.api.ApplicationV2.html) и [v14](https://foundryvtt.com/api/v14/classes/foundry.applications.api.ApplicationV2.html); меню — [ClientSettings.registerMenu](https://foundryvtt.com/api/v13/classes/foundry.helpers.ClientSettings.html). Lifecycle проверен тестовой базой, включая вставку content в DOM после `_replaceHTML` и сохранение черновика при rerender. Сам Foundry в этой среде не запускался: реальный settings dialog, темы, узкая ширина, мир и серверный перезапуск остаются ручной проверкой. Это не проверка лицензированного runtime.

Ограничения: проверена только 1.9.10 и targets Foundry 13–14; два setting не атомарны; несколько клиентов мастера используют last-write-wins; сверку нужно запускать после удаления/ошибок или открыть редактор снова. Установка: только `dist/skybricate.zip` рядом с обычным Fabricate. После экспериментальной сборки прежнего варианта нужно восстановить официальный Fabricate 1.9.10 без изменения world data.
