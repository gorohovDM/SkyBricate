## 1. Категории и данные

`src/systems/CraftingSystemManager.js:457` — список `componentCategories`; `:2105` — одиночное поле `component.category`; `:5397` и далее — массовое назначение категории. Это связь «одна категория у компонента; много компонентов могут иметь одну категорию», не взаимно-однозначная связь.

Категории Fabricate нормализуются как строки. Нельзя молча считать их стабильными UUID: переименование/удаление требует согласования связей и знаний в SkyBricate. Собственные свойства должны иметь стабильные ID. Минимальные ключи хранения:

- настройки и назначения: `craftingSystemId`;
- знание обычного свойства: `actorId + craftingSystemId + categoryKey + propertyId`;
- знание особого свойства: `actorId + craftingSystemId + componentId + propertyId`.

Каталог SkyBricate и назначения предлагается хранить в собственных world settings, знания — в своих Actor flags. Не добавлять произвольные поля внутрь объектов Fabricate: менеджер нормализует перечисленные поля и не предоставляет подтверждённого общего хранилища расширений в этой версии. Экспорт системы Fabricate сам по себе данные SkyBricate не переносит; отдельный экспорт сейчас не входит в объём.

## 3. Интерфейс игрока

`docs/api/index.md:1093–1258`, `src/ui/playerExtensions.js`:

`game.fabricate.api.playerExtensions.registerPlayerNavProvider({apiVersion: 1, id, tabs, mount})`.

`mount({target, tabId, context})` синхронный, возвращает cleanup. `context.actorId` отражает выбранного персонажа; смена контекста вызывает remount; `context.requestRemount()` обновляет свою поверхность. Регистрация из `init` с однократным fallback `ready`, вооружённым внутри `init`; обращения к сервисам после `fabricate.ready`.

Это подтверждённый публичный способ добавить собственную вкладку. Он не заменяет автоматически штатные chips эссенций в Alchemy Workbench. Свойства SkyBricate не следует зеркалировать в публичные native essences: иначе собственная скрытая вкладка не предотвращает раскрытие через другие экраны.

## 4. Путь штатного крафта и броска

`src/main.js:2576`: `submitAlchemyAttempt({actorId, craftingSystemId, submittedComponentIds, componentSourceActorIds, interactive})`.

Метод разрешает выбранные компоненты в записи `{item, componentId}` и вызывает `CraftingEngine.craftAlchemy(...)`. Для пользовательского броска нужен `interactive: true`; default для API — false.

`src/systems/CraftingEngine.js:2226`: `craftAlchemy` ищет подходящий включённый рецепт через `_matchAlchemySignature`. Без совпавшего рецепта — `disposition: "no-match"`, бросок не выполняется; возможен расход по `consumeOnFail`. При совпадении делегирует в `craft(...)` с `isAlchemyAttempt` и `alchemySubmittedItems`.

Следствие: свойства не заменяют рецепт. Свободное смешивание любых ингредиентов с генерацией нового рецепта из совпавших свойств не поддерживается этим маршрутом. Оно потребовало бы отдельного механизма, отсутствующего в принятом объёме.

`CraftingEngine.js:4246,4304,4544`:

- `system.alchemy.checkMode = none`: без броска;
- `simple`: штатная проверка успеха;
- `tiered`: штатные исходы routed check.

`src/systems/checkRoll.js:1279,1377` возвращает результат с `success`, `outcome`, `value`, `data.outcomeId`. Лимит рекомендуется привязывать к стабильному `data.outcomeId`, а не названию исхода. Для `simple` предусмотрен один лимит успешного исхода; несколько степеней успеха требуют `tiered`. При включённом лимите и `none` конфигурацию следует отклонять до расхода ингредиентов, если отдельный фиксированный лимит не согласован.

Не бросать кубик повторно. Отмена, ошибка конфигурации и отсутствие рецепта не равны успешному исходу.

## 5. Точка применения свойств до создания результата

`CraftingEngine.js:1086` — предварительное разрешение result groups до расхода. `:1125` и далее — расход; `:1159` и далее — `_createResultItems`; `:1180` и далее — фиксация успешного шага.

`_createResultItems` (`:3475`) получает `consumedItems`, `checkResult`, рецепт, шаг и набор ингредиентов. `_createSingleResult` (`:3549`) подготавливает Item data, запускает essence macros, затем result property macro, после чего создаёт предмет или увеличивает стек.

`_runPropertyMacro` (`:5244`) получает контекст:

`{recipe, craftingSystem, craftingActor, result, resolvedIngredients: [{item, quantity, ingredient}], resolvedTools, resolvedEssences, essenceSources, checkResult, step}`.

Возвращается объект `path -> value`, применяемый к Item data. Штатный механизм требует `features.propertyMacros`. Непустое изменение свойств запрещает слияние с обычным стеком: иначе Fabricate отбросил бы индивидуальные данные результата. Это важная часть корректности, а не косметика.

Варианты интеграции:

1. Штатный property macro: меньше вмешательства, но надо назначать/сочетать макросы каждому результату и включать feature; нельзя перезаписывать чужие макросы. Сам по себе этот путь не даёт обещанной прозрачной автоматизации.
2. Рекомендуемый для прототипа адаптер: ограниченная обёртка точки подготовки свойств результата на экземпляре engine, только для включённых систем SkyBricate. Сохранять вызов существующего обработчика; возвращать совмещённые обновления, включая собственные flags результата. Нельзя копировать весь `_createSingleResult`, обходить native create/stack или использовать глобальную переменную текущего крафта. Приватный метод означает привязку к версии и обязательные contract tests.

Обёртка `_runPropertyMacro` — кандидат, а не окончательно доказанная реализация: нужно проверить пути без macro UUID, feature toggle, failure-result macros, delayed/collapsed steps и совместимость с другими обёртками. Для предварительной проверки конфигурации потребуется отдельная точка до расхода, поскольку property macro вызывается уже после него.

Уточнение пользователя: применённое свойство означает реальное изменение характеристик результата, а не только метаданные. Использовать механизмы Fabricate для переноса ActiveEffect и/или property macro; собственные flags нужны только для учёта фактически применённых свойств и открытия знаний.

Штатный перенос подтверждён: `docs/effect-transfer.md:14–21` и `CraftingEngine.js:3740`. Требуются `system.features.essences`, `system.features.effectTransfer` и `recipe.transferEffects`. `_transferEffects` собирает участвующие essence IDs, находит их source Item и переносит его ActiveEffects через `resultItem.createEmbeddedDocuments`. Отдельно `_runEssencePropertyMacros` (`:3931`) меняет поля Item перед созданием при включённых `features.propertyMacros` и `features.essences`.

Эти механизмы не имеют собственного лимита SkyBricate или требования совпадения двух компонентов. Адаптер должен передавать один и тот же выбранный набор свойств обоим путям поведения, иначе макрос или перенос эффекта обойдёт лимит. Один только адаптер `_runPropertyMacro` недостаточен: essence macros выполняются до него, а transfer effects — после создания Item. Не менять глобальный enabled у эссенции на время крафта: это затронет другие попытки и системы.

Приоритет исследования этапа 9 — сопоставление propertyId с поведением Fabricate и ограничение обоих путей выбранным набором. Нельзя механически зеркалировать скрытые назначения в native component essences без проверки утечек через Workbench и inventory. Нужна отдельная проверка, как предоставить Fabricate выбранные свойства на время конкретной попытки, сохранив скрытие остальных. Точные правила применения ActiveEffect к характеристикам определяются игровой системой; SkyBricate не кодирует пути характеристик конкретной системы.

Пустой/ошибочный macro или отсутствующий effect source не подтверждает применение свойства. Факт применения фиксировать после успешного изменения результата; простого наличия кандидата недостаточно. Конфликты эффектов и нескольких макросов требуют тестов и определённого порядка обработки, а не обещания, что любое настроенное изменение обязательно влияет на итоговое значение.

## 6. Фактические входы, результаты и завершение

`CraftingEngine.js:179`: immediate `consumedIngredients` содержит `{actorUuid,itemUuid,quantity,name,img}`, без componentId. `:203`: `createdResults` содержит те же ссылочные поля и фактически выданное количество. Наличие результата не означает успех: failure path тоже может создавать предметы.

Для immediate craft сохранять ID компонентов при обработке реального consumption context, не реконструировать по названиям после удаления Item. Для алхимии использовать её уже разрешённые component IDs, учитывая extras; количество одного componentId не образует пару разных ингредиентов.

`CraftingEngine.js:1499–1552`: delayed craft использует `step.preparedConsumption.consumedSummary`; там есть componentId, а восстановленный ingredient содержит `{componentId,systemItemId}`. Live Item к завершению может быть удалён. Потребуется сохранённый снимок применимых свойств/категорий на момент расхода, иначе редактирование справочника между стартом и завершением изменит смысл уже начатого крафта.

`src/systems/CraftingRunManager.js:280,329` — `completeStepSuccess`/`completeRun`; run становится `succeeded` только на последнем шаге. Шаг хранит `lastCheckResult`, `consumedIngredients`, `createdResults`. История ограничена 50 записями (`:4`), поэтому это не бессрочный журнал знаний.

`src/systems/runContainerStore.js`, `src/config/flags.js` — сохранение контейнера Actor в `flags.fabricate.fabricate.craftingRuns`.

Предлагаемый контракт открытия: собственная запись применённых property IDs и происхождения на созданном результате + успешно завершённый run. Обработка `updateActor` читает актуальный контейнер (не полагается исключительно на вложенность changes). Открывать лишь свойства конечных результатов; промежуточный успех не открывает знания. Если создание Item не состоялось, кандидат на применение не считается применившимся.

Отдельного публичного crafting-completed hook в `src/config/hooks.js` нет. Gathering hook для этого непригоден.

## 8. Согласованные правила ядра

- Обычные свойства требуют двух различных использованных component IDs; категории могут совпадать.
- Особые свойства при выключенной опции подчиняются обычному правилу.
- При включённой опции особым свойствам не нужно совпадение; они выбираются первыми и занимают места в общем лимите.
- Один propertyId считается один раз, даже если пришёл из нескольких источников. Происхождение сохраняется для открытия соответствующих категорий/компонентов.
- Открываются только реально применившиеся свойства успешного конечного результата.
- Сортировка кандидатов детерминированная: особые при включённой опции, затем настроенный порядок мастера; известность свойства не влияет на результат.

## 9. Отсечки дальнейшей разработки

Этапы 2–8 сохраняются, но этап 4 начинается с ограниченного прототипа монтажа мастерской панели. Не считать доступность произвольной manager surface доказанной.

Этап 9 разделить на отдельные запуски:

- 9а: адаптер штатного checkResult и точного состава, проверка конфигурации до расхода;
- 9б: применение свойств перед созданием Item, существующие макросы, стекование и запись фактического результата;
- 9в: delayed/multistep сценарии и интеграционные регрессии, без повторного расхода/броска.

Смысл применения свойства к Item согласован: реальное изменение характеристик штатными механизмами Fabricate. До 9а определить точный адаптер выбранного набора для effect transfer и property macros. Не начинать генератор рецептов или fork Fabricate без отдельного задания.

Обязательные будущие тесты: public provider lifecycle; смена системы GM; сохранение обычной алхимии; success/failure/cancel/no-match; outcomeId; два одинаковых component IDs; частичный и полный расход стека; extras; удалённые inputs; лимит/приоритет; неполученный результат; слияние Item; чужой property macro; промежуточные и delayed шаги; несколько GM; разделение знаний персонажей. Это план проверок, не отчёт об их прохождении.
